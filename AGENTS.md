# Ouro UI for Apple

This repository is the Swift package for Ouro HX for Apple (`OuroHX`, `OuroHXTesting`) and Ouro AX for Apple (`OuroAX`, `OuroAXTesting`, the `ouro-ax-xray` X-ray and its probe, the `ouro-ax-skills` linter and its build-tool plugin). What is true on every platform lives in core, not here.

## Pull requests merge within 30 minutes

Follow ourostack's shared rule, [every PR merges within 30 minutes](https://github.com/ourostack/.github/blob/main/agents/prs-merge-within-30-minutes.md). Finish, review and validate on your branch first, then publish with `gh ouro-pr`, which turns auto-merge on so green means merged. When a PR here shows on the [PR clock](https://github.com/ourostack/.github/issues?q=is%3Aissue+is%3Aopen+label%3Apr-clock), act on it now: merge it if green, fix the cause if red (file an issue before any rerun), rebase it if conflicted, or close it with a reason if it isn't going anywhere.

## Where things live

- **Core:** [ourostack/ouro-ui-core](https://github.com/ourostack/ouro-ui-core) holds the tokens (DTCG JSON), their generators, HX's design language, AX's claims standard and the decision records that span platforms. Its releases publish `dist/apple/OuroTokens.swift`, AX's `apple.claims.json` and HX's `components.claims.json`.
- **Web:** [ourostack/ouro-ui](https://github.com/ourostack/ouro-ui) (becoming `ouro-ui-web`) holds the React components and AX's TypeScript kit. `OuroAX.Outcome` and `OuroAX.Problem` mirror its `ax-outcome` and `ax-problem` field for field.
- **Here:** Swift only. Package decisions are in `docs/decisions/`.

Ouro uses Ari's personal Apple developer account only, never the work (Microsoft) account or anything in ~/.config/tandem-signing.

A move, split or rename isn't done until every repository whose readers are affected says what moved, where it went and the rule for new work, in its README and AGENTS.md, in the same change. Then open an issue labelled `moved` in each old repository (create the label if it's missing), saying what moved, where it went and the rule for new work, and close it once the old home's README and AGENTS.md say so.

## Look around first

Meerkat mode: look around first. Before you design or build something new (a component, a kit, a standard, a tool or a platform target), look for prior art to adopt or borrow, and do it again for every decision record: give the record a "Prior art" section that links each find and marks it adopt, borrow, watch or ignore (Ari, 2026-11-03: "make it a standing rule for all the ouro ui stuff!!").

## Tokens come from core, by release

- `Sources/OuroHX/Tokens/OuroTokens.swift` is generated by core. **Never edit it.** `core-provenance.json` pins the core tag and the file's SHA-256, and CI (`python3 -I scripts/check-provenance.py`) fails when the file, the pin, core's `dist-manifest.json` or the release asset disagree by one byte.
- **A token bump** is its own PR:
  1. Download `OuroTokens.swift` from the new core release (`gh release download vX.Y.Z -R ourostack/ouro-ui-core -p OuroTokens.swift`).
  2. Copy it over the vendored file, set `coreTag` and the file's hash (from the release's `dist-manifest.json`) in `core-provenance.json`.
  3. Run `swift test` and the gallery captures; name the core tag in the PR title and in the README's "Meets core" line.
- A token change starts in core (and, while web still owns its CSS, in web first). A missing token is a core PR, never a Swift constant here.

## Names match web

- A component or helper that exists on web keeps web's name: `Button`, `Dialog`, `EmptyState`, `Banner`, `Sheet`, `Toast`. Colour names are HX's CSS variables in camel case (`--primary-foreground` is `primaryForeground`).
- Every public type starts with `Ouro`, lives under `OuroAX`, or, in a kit named `Ouro<Kit>`, starts with the kit's name: `Feel*` in `OuroFeel`, `Reins*` in `OuroReins`. A name never carries a platform: it is `OuroHX`, not `OuroHXApple`, and "Apple" appears only after "for" in prose.

## Components

- `Sources/OuroHX/Components/` holds `OuroButton`, `OuroEmptyState`, `OuroBanner`, `.ouroSheet` and the toast. Each
  resolves its colours as a palette value (`OuroButtonPalette` and friends) that raises every label to 5:1, a margin over 4.5 (7:1
  under Increase Contrast) on what is behind it; a new component does the same, and `ContrastTests` covers it in
  every theme.
- Behaviour is core's [component claims](https://github.com/ourostack/ouro-ui-core/blob/main/standard/hx/components.md),
  vendored as `Sources/OuroHXTesting/Resources/components.claims.json`. A new claim starts in core. Every claim needs
  a named Swift test, listed in `Tests/OuroHXTests/ClaimCoverageTests.swift`, which fails on a claim with none.
- A component change runs the unit tests, the snapshots (`__Snapshots__/macOS-<major>`) and the gallery UI tests
  (README, "The gallery"), and adds its page to the gallery.
- Spacing follows web's metrics until core has spacing tokens. Decisions: `docs/decisions/2026-11-04-hx-components.md`.

## Claims

A factual sentence is a claim on every surface: Markdown, DocC, code comments, a pull request's title and body. Give each its primary source (a file, a test, a command's output or a link) and, where one exists, the check that proves it. Credit the app a piece came from (Spoonjoy, Gatefold) in its DocC article.

## Working here

- Swift 6 language mode, strict concurrency. The floor is iOS 18 and macOS 15; a newer API goes behind `#available`, never a raised floor.
- Siri AI Developer Preview code (tool intents, SiriEvaluations) sits behind `#if canImport(SiriEvaluations)` or `#if OURO_SIRI_AI_SDK || canImport(AppIntents, _version: 301.2)`, so the package builds with Xcode 27.2. CI's `siri-ai-sdk` lane compiles it when the runner image has Xcode 27.3 or later.
- Before you push: `swift build --build-tests`, `swift test`, and `sh scripts/docc.sh`. Keep DerivedData inside `.build/` (`-derivedDataPath .build/...`).
- Never switch `xcode-select` on a shared Mac; use `DEVELOPER_DIR=... <command>`. `scripts/select-xcode.sh` is for CI only.
- Every change goes through a pull request, merged when CI is green. Releases are tags `vX.Y.Z`, made as
  [RELEASING.md](RELEASING.md) says, which includes the component claims run locally on iOS 27.
- CI runs on GitHub's free hosted runners (`ubuntu-latest`, `macos-26`) for everything Xcode 26 can build; fence iOS 27 and Xcode 27 code on the SDK, with `#if canImport(Module, _version: X)` against the framework version that first declares it, and `#available`, so it does. Never fence an SDK API on `#if compiler(...)`: Xcode 27.0 and 27.1 have Swift 6.4 with older SDKs (#6). The `oldest-xcode-27` lane builds with them and prints each SDK's SwiftUICore version. The billed `xcode-27` runner is capped by a $15-a-month budget on this repository and runs only Xcode 27 and iOS 27 checks, only on pushes to `main` and on releases, never on pull requests. It is removed once the free image ships Xcode 27: move its jobs to `macos-26` and delete their `if:` gates. Never add a self-hosted runner.
- Ruleset "main: PR-tier checks" requires What this change touches, Core provenance, Build/test/DocC, Gallery UI tests and Ouro Feel catches every genre's bug. A simulator job skipped by the `paths` job reports success, so keep each required job's name fixed and skip it with a job-level `if:`, never a workflow-level path filter. The Gallery UI check is an ubuntu job that passes only when `Gallery build for testing` and all three `Gallery UI shard` jobs passed (or the change doesn't touch the gallery); the shards split the tests by measured time in `scripts/gallery-shards.py`, whose `check` fails the `paths` job when a new gallery test or audit page is in no shard. Open a PR with auto-merge on (`gh pr merge --auto --squash`).
- Pull requests run the simulator jobs only when they change what those jobs link (`ci.yml`'s `paths` job); pushes to `main` and releases run all of them, plus the gallery's hitch probe. A red `main` is fixed by whoever merged the change that turned it red, before their next pull request; if that agent is gone, the next agent to open a pull request here owns it. A new simulator job uses `scripts/ci-simulator.py` (boots while the build runs, one fresh device on a hung boot) and `build-for-testing` then `test-without-building`.
- Other agents adopt this package in their apps (Gatefold, Spoonjoy, Ouro MD). Never edit their repositories from here; offer a PR through their own process.

## The X-ray

- `Sources/OuroAXTesting/Resources/apple.claims.json` and `Sources/OuroHXTesting/Resources/components.claims.json`
  are core's release assets, byte for byte, pinned in `core-provenance.json`. Change claims in core, then bump here.
- `OuroAXTesting` never imports AppIntentsTesting, so `ouro-ax-xray` runs on any Mac; only `OuroAXTestingProbe` does,
  inside the template's test bundles.
- Run the behaviour stage only through `scripts/xray-probe.sh` or a simulator you created; refusal runs need
  `--disposable`. Build the app, the probe and the X-ray with one Xcode whose AppIntentsTesting matches the OS.
- After changing `SiriScenarioSet`, regenerate the files in `Examples/SiriScenarios` with `ouro-ax-xray scenarios`.

## Ouro Feel

`OuroFeel` and `OuroFeelCore` check how an app feels, deterministically, from a UI test: one check per genre of jank
(`FeelGenre`). Guide: [docs/ouro-feel/README.md](docs/ouro-feel/README.md). Decision:
`docs/decisions/2026-11-05-ouro-feel.md`.

- **Before a taste review, run the checks.** A reviewer never re-tests by hand a genre Feel covers; what is left for a
  person is [docs/ouro-feel/taste-rubric.md](docs/ouro-feel/taste-rubric.md).
- **Genres and their checks:** the way back (`feel.wayBack`), overlay dismissal (`feel.overlays`), inside the window
  (`feel.insideWindow`), tap landing (`feel.tapLanding`, `feel.osBaseline`), double-draw, jump after landing, late
  or lingering chrome, snap with no transition and settle time (`feel.film` then `doubleDraws`, `jumps`, `chrome`,
  `snaps`, `settles`), place stability (`feel.place`), and hitches as a measure (`FeelHitches`, `measureHitches`).
- **Copy-paste:** `let feel = OuroFeel(app); feel.expect(feel.wayBack(from: [.launch]))`. `expect` fails the test;
  `record` reports without failing.
- **Cold, not warm:** `scripts/ouro-feel-cold.sh --project P --scheme S --test Target/Class/method --runs 5`. A result
  it did not start is labelled "not labelled, treat as warm". Never add `-retry-tests-on-failure`.
- **Quote reports as written:** simulator or device, cold or warm, which clock, and inference marked. Never claim a
  hitch figure from the simulator as a device result. A "could not check" failure (findings marked `(not checked)`) is
  not jank found: fix the test or rerun it.
- **A rule change is a core change with a unit test** (`Tests/OuroFeelTests`), and the fixture
  (`Examples/OuroFeelFixture`, bug behind `-bug 1`) must still fail on each bug and pass without it.
- Ouro Feel lives in its own targets and folders (`Sources/OuroFeel*`, `docs/ouro-feel`, `Examples/OuroFeelFixture`);
  keep component work out of them.

## Ouro Reins

`OuroReins` lets agents drive an app's screens as state and actions, headless (`ls`, `do`). Guide:
[docs/ouro-reins/README.md](docs/ouro-reins/README.md); agent skill: [docs/ouro-reins/SKILL.md](docs/ouro-reins/SKILL.md);
decision: `docs/decisions/2026-11-05-ouro-reins.md`.

- `OuroReins` never imports SwiftUI or XCTest; it must link into an app's UI-free core.
- `ReinsSocketServer` stays under `#if DEBUG`; `scripts/check-reins-release.sh` (CI) proves the release build has none
  of it.
- A behaviour journey runs under `ReinsNetworkGuard`. A failure there means a missing fixture: inject it through the
  type's constructor; never loosen the guard.
