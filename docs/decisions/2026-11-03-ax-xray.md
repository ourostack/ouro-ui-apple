# 2026-11-03: the App Intents X-ray

Status: accepted (W4 of the HX and AX native program). The claims and why they exist are core's
[Ouro AX for Apple decision](https://github.com/ourostack/ouro-ui-core/blob/main/docs/decisions/2026-11-03-ouro-ax-for-apple.md);
this record covers how this package checks them.

## Decision

1. **`ouro-ax-xray` checks a built app from outside, by bundle identifier, in two stages.**
   - **Metadata**, on the host: it reads `Metadata.appintents/extract.actionsdata` in the `.app` (iOS or macOS layout) and
     lints any `.skillsbundle` inside it with `OuroAXSkillsLint`. That is the inventory the system registers, so it
     lists every intent, parameter, entity, query and App Shortcut with its title and description. AppIntentsTesting
     has no API that lists or describes definitions (27.2's interface looks them up by name only), so the inventory
     cannot come from there.
   - **Behaviour**, in a test bundle: `ouro-ax-xray plan` writes a probe plan from the metadata;
     [Templates/XrayProbe](../../Templates/XrayProbe) runs it with AppIntentsTesting (`OuroAXTestingProbe`) and
     prints the result between `OURO-AX-PROBE-BEGIN` and `OURO-AX-PROBE-END`; `ouro-ax-xray --probe <log>` merges it.
2. **It is a test-plan template, not only a command,** because AppIntentsTesting runs inside a test bundle. Apple's
   [essentials article](https://developer.apple.com/documentation/appintentstesting/testing-your-app-intents-code)
   puts it in a UI testing bundle that launches the app. A plain process loads the framework as far as the dynamic
   linker, but SwiftPM cannot give an executable the framework search path when the package is used as a dependency,
   so the command never links it. On both platforms the template is a UI test bundle with an empty host app that
   launches the app under test by bundle identifier. XCTest has to launch it: AppIntentsTesting talks to a runner
   service that exists in the app only then. A first macOS lane used a plain test bundle against an app the script had
   opened, and every call failed with "Failed to resolve actor for key …RunnerServiceDispatcherActorProtocol", then
   "transport cancelled". On macOS the UI test bundle needs Automation Mode, which hosted runners have and a person's
   Mac enables with `automationmodetool` (an administrator's step). A call that never reaches the app skips its claim
   with that reason; it never fails the app. The UI test bundle reached the app on the second run, and macOS then refused the calls
   (AppIntentsServicesSecurityErrorDomain 800, "does not have permission"): on macOS, AppIntentsTesting runs only for
   a test bundle signed by the app's own development team, which an ad-hoc-signed CI build is not. The iOS simulator
   does not ask. So CI's macOS lane checks that the refusal is reported as a skip that says to sign both with one
   team, and a full macOS run needs an Apple Development certificate, which our CI secrets do not hold (they hold
   Developer ID). An app's own CI, signing with its team, gets the full stage. The iOS lanes retry the probe once,
   because the simulator's wait for the app to go idle hung once in two runs.
3. **The behaviour stage runs only with an Xcode whose AppIntentsTesting matches the OS.** Built with Xcode 27.2, the
   probe fails to load on macOS 27.0 and in the iOS 27.1 simulator: `AppIntentsTypeSupport` lacks
   `PropertyContainerElement.valueExpression`. CI's `xray` job therefore pins Xcode 27.1 to the iOS 27.1 simulator,
   Xcode 27.0 to the iOS 27.0 simulator, and Xcode 27.1 to the image's macOS 27.0.1, and builds the fixture with the
   same Xcode. `scripts/xray-probe.sh` does the whole stage and is what an app's CI calls. On the first run (PR #2), both iOS lanes ran the
   whole stage: the fixture's notes resolved by identifier (3 of 3) and Spotlight held all 3.
4. **Every probe reads, except refusals and import read-backs.** The probe asks each entity's query for suggested and
   all entities, looks them up again by identifier, queries Spotlight, reads view annotations, and exports one entity.
   Reading that export back runs the app's own import code, which may create a record, so it runs only with
   `--disposable`, as refusals do, and the report's "reads only" check is false whenever either ran.
   Refusals run each intent whose required parameters are all entities with references made up so nothing matches
   (`ouro-ax-xray-missing-0`), and they run only with `--disposable`: `xray-probe.sh` passes it for the simulator it
   creates; on a person's Mac they stay off unless asked. The report lists each run under `effects`. What the first run showed: App Intents resolves the made-up reference to nothing and
   asks for the parameter again (AppIntentsServicesExecutionErrorDomain 206, which AppIntentsTesting's
   auto-confirming runner cannot answer), the way Siri asks "which one?". So the intent's own `perform()` never runs,
   and neither does its error. That is the system doing the right thing, not the app failing, so the X-ray skips
   `intent.error-names-fix` with that reason. Until AppIntentsTesting can answer a value request, checking an app's
   own errors falls to a person.
5. **Web's report shape, plus what an App Intents report owes its reader.** JSON, Markdown and HTML as web's ax-xray
   writes them (`claimSet {version, hash}`, `target.commit`, `summary`, `claims`, `results`), with
   `checker.platform: "apple"`, an app target, and a `coverage` section that says, lane by lane, what ran, what it
   settled and what is open, starting with the line that the report does not prove what Siri will do. The claim set's
   hash is the same canonical-JSON SHA-256 core computes, and a test pins it.
6. **What a lane cannot check is skipped with the reason, never failed.** Metadata from before the 27.3 SDK cannot mark
   tool intents or carry property descriptions, so `intent.tool` and `entity.property-description` skip and name the
   generator. A probe that finds no content skips and says to add some. An entity that exports but imports nothing skips the round trip, since there is nothing
   to read back; the probe exports as the first type the metadata lists, because exporting with no type failed with
   `TransferableError` 3. A missing skills bundle skips, since app skills
   are optional. Person claims always skip with a concrete to-do built from the inventory.
   Two checks that depend on 27.3 metadata, `intent.tool` and `entity.property-description`, skip rather than fail on a
   27.3 build until a 27.3 fixture pins the field names, since no one here has seen that metadata yet.
7. **With no `must` claims, conformance says so.** Claim set 0.1.0 is all `should`, so the verdict line reads
   "Conforms, trivially" and points at the findings. An app with no App Intents metadata does not conform: that is the
   Gatefold baseline.
8. **Siri scenario sets are data.** `AXXray.SiriScenarioSet` (JSON) holds each scenario's kind, turns and expected
   calls, finds, loads and reply. `ouro-ax-xray scenarios` checks a set against the app's metadata (every intent,
   parameter and entity must exist; every wording kind must appear) and writes a Swift Testing file behind
   `#if canImport(SiriEvaluations)`, one test per scenario, that appends each run's pass or fail to
   `$OURO_AX_SIRI_RESULTS`; `ouro-ax-xray --siri` reads that file. Starter sets for Spoonjoy and Ouro MD are in
   [Examples/SiriScenarios](../../Examples/SiriScenarios).
9. **The claims are vendored like tokens.** `Sources/OuroAXTesting/Resources/apple.claims.json` is core v0.2.0's
   `apple.claims.json`, pinned in `core-provenance.json`.

## What running the Siri half needs

- Xcode 27.3 beta (the SiriEvaluations framework and `@AppIntent(.tool)` are in its SDK only).
- A device on a 27.3 beta OS that supports Apple Intelligence, with Apple Intelligence and Siri on. App skills do not
  load in Simulator.
- The app built and signed by the same development team as the test target, installed on that device, signed in, with
  the content each scenario's `needs` names.
- A test target holding the generated file, run five times (`-test-iterations 5`) with `OURO_AX_SIRI_RESULTS` set;
  then `ouro-ax-xray --app <path.app> --siri <that file> --siri-on "<device and OS>"`.
- Unverified until then: the generated file compiles only against the 27.3 SDK, which this repository's CI does not
  have yet. Its calls follow the SiriEvaluations documentation; the `intentsAllPass` and `skillsLoadedPass` metrics are
  the two the documentation names, so `finds`, `onscreen` and `response` are graded in Xcode's report but not yet
  recorded for the X-ray.

## Prior art

| Find | What it does | Verdict |
|---|---|---|
| Web's [ax-xray](https://github.com/ourostack/ouro-ui/blob/main/registry/ouro/ax/xray.ts) | Black-box X-ray of CLI, HTTP and MCP surfaces against the claims | **Adopt** its report shape, renderers, admission rule and "act on nothing a person would miss" |
| [os_intents_cli](https://pub.dev/packages/os_intents_cli) `doctor` | Reads `extract.actionsdata` from a built bundle to list what the system sees, and checks drift in CI | **Borrow**: the metadata stage is the same idea, extended from listing to checking claims |
| [action-relay](https://github.com/tarqd/action-relay) | Parses `extract.actionsdata` into MCP tools | **Ignore**: executing intents needs SIP and AMFI off |
| Apple's [AppIntentsTesting](https://developer.apple.com/documentation/appintentstesting) | Out-of-process intent and query runner | **Adopt** for the behaviour stage |
| Apple's [SiriEvaluations](https://developer.apple.com/documentation/sirievaluations) | Scenario runs through Siri with pass-rate metrics | **Adopt** as the generated tests' target |
